1    Completion status and evidence boundary

This report records the completed ConfigStream implementation and its accepted evidence
through 25 October 2026. The registered implementation, local deployment path, correctness
checks, comparative processing campaign, storage observations, dashboard views, and evidence
packaging are reported in full. The report does not reduce completion to a percentage. It dis-
tinguishes completed project scope from broader claims that were never part of the accepted
evidence boundary.
The central question is whether a streaming system can preserve enough identity, event-time
information, provenance, and validation evidence to support trustworthy configuration-history
analysis. ConfigStream addresses this question by combining Kafka ingestion, stateful Spark
Structured Streaming, authoritative Parquet history in MinIO, rebuildable search projections,
and a read-only API/dashboard. The design makes a deliberate separation between the historical
record and the indexes used to browse it.
The project is complete for the defined scope. The remaining items below are bounded ex-
tensions, such as multi-node high availability or a full paced RIS capacity study; they are not
missing sections of this report and are not silently treated as completed results.

2    Problem and research questions

Configuration history is easy to store incorrectly. A system that compares the previous message
with the current message can silently construct the wrong transition when messages arrive out
of order. A search index can make a result look available while the authoritative history is
incomplete. A throughput number can also be misleading when one workload reports rows per
second and another reports occurrences, files, or bytes.


                                                1
ConfigStream                                                                         Project report


ConfigStream therefore treats a configuration change as a provenance-bearing temporal record.
A change is meaningful only when the system can identify the asset, order versions using the pro-
ducer’s version semantics, reconstruct adjacent states, and retain enough evidence to reproduce
the resulting diff or alert.
The checkpoint evaluates three research questions:

    1. RQ1: Can ConfigStream reconstruct adjacent configuration states correctly under out-of-
      order arrival, duplicates, bounded buffering, and restart-sensitive streaming execution?

    2. RQ2: Does a lake-first storage boundary preserve a trustworthy historical record while
      allowing search and API projections to be rebuilt independently?

    3. RQ3: How should correctness, throughput, latency, storage growth, and resource use be
      measured across workloads whose units and semantics are different?

The current evidence answers the implementation portion of these questions positively for the
tested scope. It does not yet support claims about cluster-wide scalability, HA, or universal
configuration parsing.


3     System design

3.1    Architecture at a glance

Figure 1 summarizes the architecture in the form used for the paper. The figure separates
four ideas that are often mixed together in an engineering diagram: the typed record entering
the system, the event-time state transition, the publication boundary, and the evidence-aware
evaluation loop.
The implemented path is:

    1. a source or generator publishes typed snapshots to Kafka, keyed by asset id;

    2. Spark Structured Streaming validates records, applies event-time watermarks and identifier
      deduplication, and maintains bounded per-asset state;

    3. the processor pairs adjacent producer versions, normalizes the two states, computes a de-
      terministic diff, evaluates configured rules, and emits diagnostics when state is incomplete;

    4. the commit boundary writes authoritative history and derived evidence to MinIO/Parquet;

    5. Elasticsearch, FastAPI, and the dashboard expose rebuildable metadata and read-only
      views for inspection.


3.2    State and pairing policy

arrival order of config.events, and it does not require the config.assets topic to compute
the core diff. For each asset, the processor keeps a bounded version buffer. After sorting by the

A record that arrives late can therefore complete a transition that would be invalid under an
arrival-order implementation.
The code stores the version in ConfigSnapshot.version as a producer-assigned integer. The
notation v1, v2, and v3 below is an example, not a fixed dataset convention. For arrival order
v1, v3, v2, the buffer first retains [v1,v3] and emits no adjacent edge. When v2 arrives within
the retention policy, the sorted state is [v1,v2,v3] and the processor emits v1–v2 and v2–v3.
It does not emit v1–v3 as an adjacent streaming transition. The pure comparison helper can
accept non-consecutive endpoints and report a version gap; that separate API boundary must
not be confused with the streaming emission rule.
The buffer is intentionally bounded. When a version gap, eviction, duplicate, or malformed
record prevents a complete transition, the system records a diagnostic rather than inventing a
diff. This choice makes incompleteness visible and keeps the correctness contract explicit. The
default policy retains at most 32 versions per asset, applies a ten-minute event-time watermark
delay, and clears inactive state after a 30-minute event-time timeout. The accepted TerraDS
replay used its registered run settings, which must be reported separately from these defaults.


3.3        Common evidence contract

The common contract layer gives every record an identity, a time interpretation, and a prove-
nance reference. A ConfigSnapshot carries snapshot id, asset id, producer version, event
time, ingest time, and a raw content hash. Source-specific temporal records carry the corre-
sponding source coordinate and manifest reference. A record identity is derived from canonical

fields and a named policy; it is not inferred from a Kafka offset or from the order in which a
consumer sees messages.
This distinction determines what the system can safely claim. A repeated delivery with the
same logical identity can be suppressed or reconciled. A second record that reuses an identity
with different content is a conflict. A timestamp identifies when an observation was made, but
it does not establish which producer version precedes another. The processing code therefore
keeps identity, producer order, event time, and transport provenance as separate fields.


3.4    Configuration transformation

Only an admitted adjacent pair enters the configuration transformation. The normalizer converts
supported text into a deterministic line representation, applies the implemented whitespace and
generated-comment rules, and masks selected secret-like settings. It produces a normalized hash
while preserving the raw hash of the source bytes. These hashes answer different questions: the
raw hash identifies the received content, while the normalized hash identifies the content under
the declared policy.
The diff compares normalized lines with deterministic line-based logic. The result identifies
the old and new snapshots, their versions, the policy, and the normalized hashes. YAML rules
inspect the normalized diff and create deterministic alerts. The method supports the registered
text representation. It is not a vendor-aware configuration parser, a complete secret detector,
or proof that a proposed change is safe to deploy.


3.5    Source-specific temporal lanes

RPKI, RIS, and DNS do not pass through the configuration version buffer. They share the evi-
dence contract and the publication boundary, but each lane has its own identity and completion
condition.


RPKI.     The RPKI path decodes source chunks into canonical authorization rows and records
their source coordinates. A daily state is eligible for comparison only when the expected coordi-
nate inventory is complete, the source manifest and artifact digest validate, and the accepted-row
count and state digest agree with the observation descriptor. A transition compares two compat-
ible consecutive complete states. An incomplete daily input remains incomplete; the processor
does not infer deletions from rows that have not been observed.


RIS.   The RIS path frames MRT input and projects records into peer-prefix occurrences. Oc-
currence identity retains the frame and record coordinate. Repeated observations are not col-
lapsed into a set because multiplicity is part of the evidence. The resulting record answers an
occurrence-processing question. It does not claim to be a complete global BGP state or a count
of unique deployed routes.

DNS.    The DNS path groups measurements by the declared query, response, address, and
vantage dimensions. It carries coverage and vantage uncertainty into the output. A qualified
difference requires the declared comparison policy and the required partition or group complete-
ness. An unknown coverage or vantage value remains unknown; the implementation does not
turn it into evidence of global disappearance.


3.6    Publication and recovery

The publication boundary is lake-first. A batch writes raw provenance and typed processed
records to Parquet, inventories the files, validates byte counts and row counts, computes or
checks SHA-256 values, and writes a manifest only after the expected data is present. Readers
use the manifest to exclude partial or uncommitted batches.
Search, FastAPI, and the dashboard are derived projections. If a projection is missing or stale,
recovery reads the committed Parquet datasets, rebuilds the projection, and reconciles logical
identities and counts. A failed projection does not change the authoritative history. The bound-
ary does not make Kafka, Spark, MinIO, and Elasticsearch one distributed transaction, so the
report does not claim end-to-end exactly-once processing.


3.7    Evaluation method

The evaluation follows the same boundaries as the implementation. Configuration replay checks
snapshot identity, adjacent-pair identity, normalized output, alert identity, diagnostics, lake
contents, and manifest integrity. RPKI checks complete-state membership, digests, transition
equality, storage layout, and query equality. RIS checks framed occurrence identity and multi-
plicity. DNS checks qualified groups while retaining coverage and vantage fields.
Every performance result keeps its workload unit and processing boundary. TerraDS reports
snapshots and adjacent pairs for an end-to-end replay. The matched B0/B2/B3 campaign
compares one normalized projection under fresh processes and excludes source parsing and
production state finalization. RPKI, RIS, and DNS rates are not pooled. This separation is
part of the method because a row, an occurrence, a file version, and a measurement group do
not represent the same object.


3.8    Normalization, diff, and publication

Normalization is deterministic and line-oriented for the supported configuration representation.
The system retains a raw hash and a normalized hash, which lets the evaluator distinguish byte-
level changes from semantic changes under the chosen normalization policy. Selected secret-like
keys are masked according to the implemented rule set. The current method should not be
described as a universal parser or a universal secret detector.
The publication rule is lake-first. A commit manifest records the relationship between au-
thoritative Parquet artifacts and rebuildable projections. If Elasticsearch or the dashboard is
unavailable, the historical record remains the recovery source. This design does not remove all

4.2    End-to-end TerraDS replay

The accepted TerraDS replay processed 10,188 snapshots and formed 3,683 adjacent diffs. It
committed 29,402,997 raw and processed Parquet bytes, emitted zero alerts and zero diagnostics,
and completed after the publisher drained in 68.742 seconds. The publisher rate was 500.023
snapshots/s. The accepted logical rate, which includes the workload’s logical-byte interpretation,
was 148.205 snapshots/s.
These numbers demonstrate an end-to-end path under the accepted replay conditions. They
do not establish a production capacity limit. A supplemental headroom replay used the same
history and pairs but produced 29,346,912 Parquet bytes and 139.565 accepted snapshots/s;
because the runs were not a matched comparison, the difference should not be presented as a
model improvement.

4.4   Storage and resource observations

The matched campaign produced 1,622,766,994 Parquet bytes and 1,623,023,143 MinIO names-
pace bytes. Retained growth was 3,869,485,576 bytes, below the amended 6 GiB limit. The
peak tree was 1,612,824,576 bytes, the minimum observed guest RAM was 4,191,440,896 bytes,
and no resource failure occurred. The aggregate processing time was 502.981 seconds, below the
7,200-second acceptance limit.
The initial pilot failed because a SQLite connection was used from the wrong Spark callback
thread. That attempt produced zero committed files and is retained as a failed trial. The
corrected retry passed. Reporting both attempts matters because the failure identifies a real
integration boundary rather than an unexplained missing result.

5.2     Outside the accepted claim

This report does not claim a full paced RIS capacity comparison, the H3 branch, a multi-node
high-availability deployment, recovery guarantees under realistic component loss, or end-to-end
exactly-once processing. These are deliberately bounded extensions. They are not evidence that
the implemented and accepted project scope is only partially complete.
Hardware and operating-system metadata, reference formatting, author contributions, data/code
availability, and the exact relationship between each table and its source artifact remain human
approval items for formal submission. They do not alter the reported experimental results.

8      Optional extensions beyond the completed scope

If a future version needs broader deployment claims, the following extensions should reduce
uncertainty before adding new components:

    1. Close the evidence ledger. Attach every reported number to a run manifest, envi-
       ronment record, artifact path, and acceptance criterion. Record the exact hardware and
       operating-system details.

    2. Finish the deferred comparisons. Run the approved paced RIS experiment and H3
       only if their hypotheses and denominators are fixed in advance. Keep them separate from
       the accepted matched campaign.

    3. Test recovery and projection rebuild. Delete or make unavailable a rebuildable
       projection, reconstruct it from Parquet and the manifest, and verify row counts, hashes,
       and query results. Then document the limits of the recovery guarantee.

    4. Expand correctness tests. Add adversarial cases for duplicate identifiers, late versions,
       version gaps, buffer eviction, malformed records, and restart boundaries. Check both
       positive diffs and diagnostics.

    5. Prepare the final presentation. Use one architecture figure, one state-reconstruction
       example, one evaluation table, one evidence dashboard view, and one limitations/next-
       steps slide. Avoid a service inventory as the main story.

10     Questions and detailed results

This section is retained as a reference during a presentation or oral examination. The central
results are: 10,188 TerraDS snapshots and 3,683 adjacent diffs in the accepted replay; zero alerts
and zero diagnostics in that run; 27 exact trials in the corrected matched campaign; identical
normalized outputs across B0, B2, and B3; 1,622,766,994 Parquet bytes and 1,623,023,143 MinIO
namespace bytes in the matched campaign; 3,869,485,576 bytes of retained growth, below the
amended 6 GiB limit; and 502.981 seconds of aggregate processing time, below the 7,200-second
acceptance limit.
The interpretation is deliberately narrow. The evidence establishes the implemented processing
and storage paths under the recorded local conditions. It does not establish cluster-wide capacity,
multi-node HA, universal configuration parsing, or end-to-end exactly-once semantics. The
accepted RPKI storage experiment supports a representation trade-off within its selected scope:
analytical storage fell by 92.6% for R2, while the broader measured local accounting boundary
fell by 17.5%. These are different denominators and must not be merged.


11     Conclusion

ConfigStream is complete within the declared project scope. Its contribution is the separation
of temporal state reconstruction, authoritative history, and rebuildable read projections, backed
by explicit workload semantics and evidence receipts. The report’s main limitation is not an
unfinished core workflow but the deliberate boundary around broader deployment claims. Any
future extension must add evidence, not reinterpret the current local results.
